# Four-minute-thirty-second demonstration

Use the real application and real camera footage. Label shortened timers as Demo.
Do not present the synthetic replay as a webcam result. Do not claim a successful
AWS deployment until its receipt and an AWS-sourced decision trace exist.

| Time | Show | Narration / purpose |
|---|---|---|
| 0:00-0:25 | Team members and Sora Home | Introduce names/roles, target users and the forgotten-work-break problem. |
| 0:25-0:50 | Start and calibration | Personal reference, local OpenCV 5 pipeline; webcam permission remains user-controlled. |
| 0:50-1:35 | Sustain a lower position, reminder, return to reference | Show that observed recovery changes the next action and closes the goal. |
| 1:35-2:00 | Another unresolved posture case, then Agent activity | Show the single alternative break offer and the observation/decision/tool trace. |
| 2:00-2:35 | Cup/bottle approach, contact, retreat; water record | Demonstrate only successful actual detections. Also show a miss and manual confirmation/undo. |
| 2:35-3:00 | Dismiss, snooze, tracking loss, Quiet mode | No repeated questions, no unknown-as-recovery, human control. |
| 3:00-3:25 | Architecture and actual AWS trace | Identify local image processing and remote policy execution; disconnect to show local fallback. |
| 3:25-4:05 | Evaluation table and failure cases | Report 75 software tests, six synthetic scenarios separately from real-video precision/recall/FPS. Fill in only measured values. |
| 4:05-4:30 | Pause/End, final product view | Camera released; summarize limits and next improvements. |

Optional meeting and straw clips can replace part of the feature section if
they work reliably in the actual recording. Keep failures visible in the report.
No need to wait 20 minutes or 24 hours on camera: use the explicitly labelled
Demo launcher. Never suggest the demo timer validates a 24-hour human study.
